# AGENTS.md

This file helps AI agents work efficiently in this repo. Read it before making changes.

## Project Overview

An all-in-one open source Islamic app (Quran + nasheeds), desktop/mobile, Spotify-like player. Display name is **Quran** (the app is literally named "Quran"; repo slug `quran`) (no "songs" branding, the user insists on **nasheed** terminology). Internal ids are all `quran` (package `quran-player`, binary `quran`, identifier `com.goldstac.quran`, data dir `quran-app`); a legacy `nasheed-app` data dir is auto-renamed on first run. The word "nasheeds" (the content) stays everywhere in UI copy. It searches YouTube via `yt-dlp`, streams audio through a local proxy, manages a persistent library, favorites, and playlists, plays Quran audio direct from CDN with reciter selection, downloads nasheeds for offline listening, and imports local MP3/MP4 files as "Your Nasheeds". NOTE: downloads were removed once by user request, then deliberately brought back on request; do not remove them again without asking.

Two app versions exist in this repo:
- **`web/`** — active Flask + TypeScript/CSS web app (the one being developed)
- **`tauri-app/`** — desktop app for testing (Tauri v2): Rust spawns `python3 web/app.py` on startup and keeps its **stdin pipe open** the whole time; the backend watches that pipe for EOF (`QURAN_STDIN_WATCH=1`) and exits when the app closes, so no orphaned backend survives. The window loads `http://127.0.0.1:5000` via a loading page. Android APKs are published as prereleases and built in CI.

## Commands

- Run the web app: `./run-web.sh` (starts Flask on `http://localhost:5000`)
- Build frontend TS → JS: `npm run build` (from repo root; compiles `web/ts/app.ts` → `web/static/app.js`). Use `npm run watch` during dev.
- Build the desktop binary: `cargo build --release` (in `tauri-app/src-tauri/`) → `target/release/quran` (gitignored). Run it directly; it spawns the Flask backend itself. If the backend lives elsewhere, set `QURAN_WEB_DIR`. If port 5000 is already held (e.g. `run-web.sh` running), it just connects to the existing server.
- Backend tests: `python3 -m pytest` (run from `web/`; dev deps in `web/requirements-dev.txt`, installed with `--break-system-packages`). The suite redirects `$HOME` to a temp dir before importing the app, so it never touches your real `~/.local/share/quran-app` data. Type check the backend: `python3 -m mypy web/app.py`. Still verify Python loads cleanly before finishing: `python3 -c "from app import app"` (run from `web/`)
- Keep `task-board.md` in sync with the work you do (see below).
- CI: every push to `main`/`development` and every PR runs the fast `validate` job (Python import, `python3 -m pytest` from `web/`, `python3 -m mypy web/app.py`, `npm run build`, and a check that the committed `web/static/app.js` still matches `web/ts/app.ts`). The full pipeline is tag/dispatch only: `build` (three platforms, with pip/npm/Rust caching and the npm Tauri CLI) then `runtime-test` (launches the packaged Windows/macOS apps, checks the backend on `127.0.0.1:5000`, and confirms the backend exits when the app is killed), plus `android-runtime-test` (boots an API 35 x86_64 emulator after enabling KVM, installs the known-good `v1.2.1-pre-alpha.1` APK then the new build as an in-place upgrade, launches `com.goldstac.quran/.MainActivity`, checks the in-app Rust server on `127.0.0.1:5000` through `adb forward`, checks the WebView actually left the loading page via `uiautomator dump`, fails on a logcat crash, and confirms `am force-stop` kills the server; it needs no signing secrets, so it does not use the `android-signing` environment). The Android build stamps a monotonically ordered version code, requires the existing release signing key, and checks the package metadata, signature, ABIs, resource table, and 16 KB native-library alignment before upload. The test body lives in `.github/scripts/android-runtime-test.sh` because `android-emulator-runner` runs its `script` input line by line as separate shells, so the action gets the single command `sh .github/scripts/android-runtime-test.sh`. `release` then publishes with an AI-written description: the `Write release notes` step is a one-line call to `.github/scripts/write-release-notes.sh` (the release job and the smoke test below run that same script, so what is tested is what ships), which diffs the tag against the previous `v*` tag, drops pure `ci`/`chore`/`build`/`style`/`docs` commits (`refactor` stays in, so a change that was added and then taken back shows both halves), sends the rest to Groq (`POST https://api.groq.com/openai/v1/chat/completions`, secret `GROQ_API_KEY`, model from `GROQ_MODEL` (Actions variable or secret, whichever you set) defaulting to `llama-3.3-70b-versatile`) and writes `release-notes.md` for the release action's `body_path`. The model only ever writes the top part: a TL;DR plus a `## What's new` list. The step itself appends `## Changes` (the verbatim commit subjects) and `## Downloads` (the four fixed installer lines), so those two sections are exact no matter what the model does, and the sanitizer also truncates anything the model writes at a `## Changes` or `## Downloads` heading. It falls back to no TL;DR at all (just `## Changes` plus `## Downloads`) when the secret is missing, Groq returns anything but 200, or the text comes back empty, and the output is post-processed to drop code fences, wrapping quotes, blank leading lines and every dash that is not an ASCII hyphen (the model reaches for U+2011), so the no-em-dash and "nasheeds not songs" rules hold even if the model disobeys. The prompt also tells it not to describe a change that an entry further down the list takes back, which is how a reverted feature stops being advertised as new. The path is provable before a tag: a dispatch-only `release-notes-test` job runs `.github/scripts/release-notes-smoke-test.sh`, which writes the notes twice (once with Groq, once with `GROQ_API_KEY` blanked out to prove the fallback), prints both in the run log, and fails unless the structure holds: exactly one `## Changes` and one `## Downloads` heading, the four installer lines, no dash but an ASCII hyphen, a TL;DR as the first line rather than a heading, a `## What's new` with 3 to 6 bullets under 160 words, no "songs", and byte-identical pipeline-written sections across the two runs. It also fails when `GROQ_API_KEY` is missing or Groq contributes nothing, so a broken key shows up before release day. Its `notes_version` dispatch input labels the preview, and `notes_only: true` skips package builds so only validation and the Groq smoke test run. Before a release tag, push to `development`, then run `gh workflow run release.yml --ref development -f notes_only=true -f notes_version=v1.2.1-pre-alpha.3`; never release until that passes.

## Critical Gotchas

1. **Port 5000 usage**: `./run-web.sh` will fail with "Address already in use" if anything else holds port 5000. Free it with `fuser -k 5000/tcp` before running. Do NOT start a background test server that holds port 5000 — the user runs the app themselves and gets blocked.
2. **`app.py` run block position**: The `if __name__ == "__main__": app.run(...)` block MUST remain at the BOTTOM of the file. If you append routes after it, they never register when run directly (only when imported). This caused a hard-to-find 404 on `/api/proxy` once.
3. **YouTube direct playback is blocked**: Browsers cannot play raw YouTube stream URLs. All playback MUST go through `/api/proxy/<video_id>`, which resolves a fresh URL via `yt-dlp -g`, caches it per video_id (`_stream_cache`), forwards `Range` headers (needed for seeking), and returns `206 Partial Content`. Clears cache entry on upstream error (expired URL).
4. **Loop feature (user's top priority)**: it kept "not working". Current behavior — loop button toggles only `off` ↔ `one` (repeats current track by doing `audio.currentTime = 0; audio.play()`). There is NO "loop all" anymore by design; the user explicitly wanted single-click = repeat current nasheed. Do not bring back the 3-state cycle without asking.
5. **Loop "one" must NOT re-fetch the stream URL** on the `ended` event — just replay `audio.currentTime = 0`. Re-fetching was the original bug (stale/expired URLs + autoplay blocking).
6. **`play()` rejections must be caught** and surfaced (toast `'Click play to start'`); a silent `.catch(()=>{})` hides autoplay-policy failures.
7. **Players served through proxy only**: `/api/stream` returns JSON metadata, but the `<audio>` element must use `/api/proxy/<id>` for its `src`.
8. **CSS mobile overrides must live BELOW the rule they override**: media queries do not add specificity, so a `@media(max-width:768px)` block placed before the section it overrides loses to the later plain rule. The settings overrides sit in a second `@media` block at the very end of `style.css` for exactly this reason. A misplaced block quietly renders the desktop layout at every width.

## File Map (tauri-app — desktop test wrapper)

- `tauri-app/src-tauri/src/main.rs` — spawns `python3 app.py` (finds `web/` via `QURAN_WEB_DIR`, manifest-relative path, or `./web`), stores the child, kills it on `RunEvent::Exit`.

This matters because the app targets SDK 36 and Android 15 enforces edge-to-edge, so without it the WebView draws under the status bar and the navigation bar and the hamburger/player bar get covered. wry calls `activity.setContentView(webView)` from the Rust thread after `onCreate`, so `onWebViewCreate` re-dispatches insets (`requestApplyInsets`) once the WebView is attached. This does not affect desktop or the web app.
- `tauri-app/src-tauri/src/lib.rs` — on Android there is no Python, so it starts the in-process Rust server instead (`server::start(data_dir, 5000)` with the app data dir).
- `tauri-app/src-tauri/src/server.rs` — the Android backend: a hand-rolled HTTP server (std TCP, no framework) that embeds `web/templates/index.html`, `web/static/app.js`, `web/static/style.css` and `web/static/app_logo.png` at compile time (`include_bytes!` via `CARGO_MANIFEST_DIR`, so `cargo` builds from the repo root need the `web/` dir present) and mirrors `web/app.py`'s routes so the same frontend runs on mobile. ## Frontend Conventions

- **Source of truth is TypeScript**: all JS logic lives in `web/ts/app.ts` and compiles to `web/static/app.js`. After editing TS, run `npm run build` so changes take effect. Never hand-edit the compiled JS.
- **Sliders are a custom component, not browser inputs**: `<input type="range">` is banned. Use an empty container div with `role="slider"` and an `id`, then build it in TS with `new Slider($('#...'))`. The `Slider` class exposes `setValue(v)` and `onInput`/`onChange` callbacks. Progress reads at 250ms interval into `seek.setValue(p)`; volume reads `vol.getValue()`. Keyboard support built in (←/→, PageUp/Down, Home/End).
- **Class names**: sidebar = `sidebar`, `nav-item`, `pl-item`; track rows = `track-row`, `track-thumb`, `track-name`, `track-channel`, `track-dur`, `track-actions`, `track-act` (with `play-act`/`fav-act`/`pl-act`/`yt-act` variants); player = `player-*`, controls `ctrl` / `play-pause`; sliders = `.slider`, `.slider-env`, `.slider-fill`, `.slider-thumb`; toasts = `.toast`; settings = `settings-card`, `settings-card-head`, `settings-card-title` (+ `gold`), `settings-card-sub`, `settings-rows`, `settings-row`/`settings-row-label`/`settings-row-value`, `settings-ctl` (right-aligned toggle + `disc-status` chip), `settings-note`, `set-btn` (+ `ghost`), `set-btn-row`, `set-input` (+ `set-input-code`), `settings-vol`, `update-progress`.
- **Settings rows are one alignment grid**: every row is `label (128px) | control | trailing right-aligned`, so values, status chips, and the button/input columns all end on the same x. Trailing bits use `margin-left:auto` for value/toggle rows; inputs have an identical width when a fixed 104px button follows them on the row (the Bot URL `Test` and Link code `Link` rows), and notes/button rows are inset `padding-left:142px` to line up with the control column. Keep it that way when adding a row.
- **Rendering**: rows are created by `makeRow(song, idx, ctx)` in `app.js`. Click handlers: single-click on row-actions buttons, `dblclick` on row to play.
- **State**: `queue` / `queueIdx` / `loopMode` / `currentSong` / `currentList` are module-level `let`s. `currentList` must be set whenever a list renders (so loop/next/prev have a queue from any view — search, library, favorites, playlist).
- **Toasts**: use the `toast(msg)` helper for user feedback (like, download, loop, playlist actions).
- **Keyboard shortcuts**: Space = play/pause, ←/→ = seek, Shift+←/→ = prev/next, ↑/↓ = volume, L = loop, M = mute, / or S = focus search.
- **Spotify QoL behaviors** (keep these intact when editing):
  - **Shuffle**: player-bar `#shuffle-btn` toggles `shuffleOn` via `setShuffle(on)`; when on, starting a track builds `queue = [current, ...shuffled rest]`; toggling off restores `preShuffleQueue`. Header `#shuffle-play-btn` = play list shuffled. Persisted (`ns_shuffle`).
  - **Auto-advance**: track `ended` plays the next queue item (unless loop one); stops (`resetPlayer`) at queue end. `nextTrack` likewise stops at end (no wrap). `playSong(..., keepQueue=true)` is used for queue-internal moves so the queue is NOT rebuilt.
  - **Loop** is off↔one only, persisted (`ns_loop`).
  - **Recently Played** nav view reads localStorage `ns_recent` (cap 50, recorded in `playSong` via `recordRecent`). **Recent search chips** (`#recent-q`) read `ns_recentq` (cap 8, saved in `doSearch`); chips show only while the search input is empty.
  - **Library**: header has green Play (`#pl-play`) + shuffle-play, sort dropdown (`#lib-sort`, modes added/title/channel, persisted `ns_sort`), rename (pencil, playlists only). `loadLib` sets `currentLibMode`/`currentLibSource` (library/favorites are reversed to newest-first). Rows in library contexts get a trash (`rem-act`) → `removeFromList` (playlist context removes from that playlist, otherwise from library) — search-result rows have no trash.
  - **See on YouTube**: every YouTube nasheed row (all views) has a `yt-act` button (YouTube brand icon) that POSTs `{url: https://www.youtube.com/watch?v=<song.id>}` to `/api/open`, which opens it in the system browser (`webbrowser.open`); the player bar has the same action (`#yt-btn`, hidden for Quran). Quran rows have no such button.
  - **Downloads**: the `dl-act` button on every YouTube nasheed row (and `#dl-btn` in the player bar) starts `POST /api/download`, spinners (`dl-active`) while running, a green check (`dl-done`) when the file is stored; clicking again cancels or removes it. `downloadedIds`/`dlActive` sets plus a 1s `/api/download/status` poll keep every row in sync, and `/api/proxy/<id>` serves the stored file, so nothing else in the player needed changing.
  - **Your Nasheeds**: `#local-add` (visible only in the `local` library view) opens the hidden `#local-file` input; each file is POSTed to `/api/local` and the view reloads. Local songs play from `/api/file/<id>`, have no YouTube/download buttons, show `Local nasheeds` as their channel, and are deleted from disk when removed from the library. Embedded cover art shows anywhere `song.thumbnail` is used (row, `#player-thumb`, media session): the backend sets `thumbnail` to `/api/local-thumb/<id>` when the file had art, so rows keep the music-note placeholder otherwise.
  - **Provided Nasheeds**: the `provided` nav view loads the shared manifest from `/api/provided`, renders cover/title/munshid rows, plays audio through `/api/provided/audio/<id>`, and downloads MP3 attachments from the same route with `?download=1`. Curate entries in `catalog/index.json`; audio and cover filenames are keyed by the lowercase `id`, and `catalog/README.md` documents the format. - **Discord presence** (opt-in): the frontend (`web/ts/app.ts` "DISCORD PRESENCE" section) just forwards the current song to the backend, which runs the actual RPC: `web/app.py` has a `DiscordBridge` that connects to Discord's local IPC socket (Linux `$XDG_RUNTIME_DIR/discord-ipc-0`, macOS `$TMPDIR/discord-ipc-0`, Windows named pipes `\\.\pipe\discord-ipc-N`) with the legacy 8-byte-header framing, handshake `{"v":1,"client_id"}` using the shared `_DISCORD_CLIENT_ID` (owned by the repo maintainer), and sends `SET_ACTIVITY` frames decorated by `_discord_decorate()`: `type` 2 (Listening), `status_display_type` 2 (so the status line shows the nasheed, not the app name), `details` = title, `state` = channel, `assets.large_image` = `_DISCORD_LOGO_URL` (the repo's `app_logo.png` via raw.githubusercontent, since Rich Presence accepts external image URLs, so the card shows the Quran logo instead of a placeholder), a `Get Quran` button linking to `_DISCORD_REPO_URL`, and a `start`/`end` timestamp pair while playing so Discord draws the playback bar (falls back to `start` only when the duration is unknown). Al-Fatihah", `state` = reciter; reciter switches refresh the presence via `applyQuranReciter`, which also keeps `currentSong.channel` in sync for the player bar). The Tauri webview/browser cannot reach Unix sockets or named pipes, and Discord's local WebSocket gateway on 6463 rejects plain handshakes, so the bridge is required. Frontend posts to `POST /api/discord` (`{enabled, activity}`, plus `remember:true` when the user flips the toggle) and polls `GET /api/discord/status` (`off|connecting|connected|no-discord`) every 2s when enabled. The status response also carries the persisted `enabled` preference, and the poll re-enables when it sees `off`, so a backend restart self-heals. The toggle is remembered authoritatively in `~/.local/share/quran-app/discord.json` (written only from the toggle, never from the `pagehide` clear; the same file also holds the `hidden` id list) and mirrored to localStorage `ns_discord`, so it survives webview or site-data resets. The bridge stays `connected` as long as Discord is up: the 2s status poll doubles as a heartbeat (`GET /api/discord/status?alive=1` refreshes liveness, and enabling posts `{enabled:true}` immediately), so it only drops the presence after the frontend goes quiet for 120s (closed or frozen tab, sending an empty `SET_ACTIVITY` first so Discord actually clears it), reconnects within 5s once activity resumes, and abandons a half-open handshake after 10s. Closing the tab clears it immediately via a `pagehide` `navigator.sendBeacon` to `POST /api/discord {enabled:false}` (a plain socket close alone left Discord showing the last activity). Per-nasheed hide/show is a row eye button (`discIsHidden`/`discToggleSong`) that keeps the id list in localStorage `ns_discord_hidden` and writes it through `POST /api/discord/hidden {ids}` (validated: strings, max 64 chars, 500 entries); `GET /api/discord/status` also returns `hidden`, and `initDiscord` adopts that server list on load (seeding the server from localStorage when the file has no list yet), so a hidden nasheed stays hidden across reloads, restarts, and webview site-data wipes, and hidden songs never push a presence. Presence is pushed on play/song change/seek (throttled every 30s in the 250ms progress interval), kept as `Paused - <channel>` when paused, and cleared on stop/reset.

## Backend Conventions

- Python 3.11+, Flask. Installed with pip via `--break-system-packages` (Arch).
- `yt-dlp` binary is at `/home/admin/.local/bin/yt-dlp` (on PATH).
- Subprocess calls to yt-dlp must include `--no-warnings --no-playlist` and a timeout.
- Library is JSON at `~/.local/share/quran-app/library.json` with shape `{"songs":[...], "playlists":[{"name","songs":[]}]}`. Songs have `id`, `title`, `channel`, `thumbnail`, `duration`, `duration_string`, `url`, `favorite` (bool), `filepath`, plus `downloaded` (bool, offline copy in `downloads/`) and `local` (bool, user-imported file in `local/`; `channel` is `Local nasheeds`). Removing a song from the library deletes its stored file (only inside the data dir).
- `/api/version` returns the app version from a single source: `QURAN_VERSION` env var (set by the desktop app from `CARGO_PKG_VERSION`) if present, else the `version` field in `package.json`. Keep version bumps in sync across `package.json`, `tauri-app/src-tauri/Cargo.toml`, `Cargo.lock`, and `tauri.conf.json`.
